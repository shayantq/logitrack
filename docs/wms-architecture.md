# معماری پایه انبارداری (WMS) — فصل ۱ تا ۵

این سند قواعد پایه، واژه‌نامه، چرخه عمر کالا و ساختار داده پایه پسینه را توضیح می‌دهد. منبع واحد نام‌ها و وضعیت‌ها در کد `app/core/wms.py` است و همین فهرست از `GET /wms/vocabulary` هم در دسترس است.

## ۱. قاعده‌های غیرقابل‌مذاکره

| قاعده | چطور تضمین می‌شود |
|---|---|
| موجودی هرگز با ویرایش مستقیم عدد عوض نمی‌شود | تنها مسیر، `stock_ledger.record()` است که همراه با یک **سند انبار** یک **گردش** ثبت می‌کند. محافظ `before_flush` هر تغییر بی‌سند در `quantity` یا `reserved_quantity` را با `LedgerViolationError` رد می‌کند. |
| وضعیت فیزیکی، کیفی، تخصیص و سند از هم جدا هستند | چهار محور جدا (بخش ۲). هر محور فقط از مسیر خودش تغییر می‌کند. |
| سند قطعی حذف یا بازنویسی نمی‌شود | ORM: ویرایش/حذف `StockMovement`، `DomainEvent` و سند قطعی متوقف می‌شود. PostgreSQL: تریگرهای مایگریشن ۰۰۲۴ حتی SQL مستقیم را رد می‌کنند. اصلاح فقط با **سند برگشت**. |
| جلوگیری از رزرو دوباره و رقابت هم‌زمان | قفل ردیف (`SELECT … FOR UPDATE`، همیشه به ترتیب `id`)، قید `reserved_quantity <= quantity` در دیتابیس، قید یکتای ردیف موجودی و `SAVEPOINT` برای ساخت هم‌زمان ردیف، و کلید یکتایی درخواست (Idempotency-Key). |

حالت نگهداری (`stock_ledger.maintenance`) فقط برای اسکریپت‌های نگهداری و داده نمونه است و هرگز در مسیر درخواست کاربر استفاده نمی‌شود.

## ۲. چهار محور وضعیت

```
             فیزیکی                 کیفی                    تخصیص                 سند
  ┌──────────────────────┐  ┌─────────────────────┐  ┌──────────────────┐  ┌───────────────┐
  │ کالا × انبار (ردیف     │  │ available  سالم      │  │ رزرو فعال         │  │ draft         │
  │ inventories)          │  │ quarantine قرنطینه   │  │ (stock_          │  │ posted  قطعی  │
  │ quantity = موجود       │  │ blocked    توقیف     │  │  reservations)   │  │ reversed      │
  │ گردش‌ها = تاریخچه     │  │ damaged    معیوب     │  │ موجودی آزاد =     │  │ canceled      │
  │                       │  │ هر وضعیت یک ردیف    │  │ موجود − رزرو      │  │               │
  └──────────────────────┘  └─────────────────────┘  └──────────────────┘  └───────────────┘
```

- **ردیف موجودی** = کالا × انبار × وضعیت کیفی (قید یکتای `uq_inventories_bucket`). فقط ردیف «سالم و آزاد» فروخته، رزرو، شمرده (انبارگردانی) و در نقطه سفارش حساب می‌شود.
- **رزرو** موجودی فیزیکی را تغییر نمی‌دهد؛ فقط آن مقدار را برای سفارش‌های دیگر قفل می‌کند. پایان رزرو: «مصرف» (حواله خروج) یا «آزادسازی» (لغو/انقضا).
- **وضعیت کالای سفارش** (`orders.stock_state`) جدا از وضعیت حمل است: `reserved` ← `issued` (بارگیری) ← `returned` (عدم تحویل)، یا `reserved` ← `released` (لغو/انقضا قبل از بارگیری).

## ۳. انواع انبار و سلسله‌مراتب

| نوع | نگهداری کالا | ارسال سفارش | رسید مستقیم | وضعیت پیش‌فرض رسید |
|---|---|---|---|---|
| عمومی، محصول نهایی، مرکز توزیع | ✓ | ✓ | ✓ | سالم |
| مواد اولیه | ✓ | — | ✓ | سالم |
| قرنطینه، مرجوعی | ✓ | — | ✓ | قرنطینه |
| در راه | ✓ | — | فقط با انتقال | سالم |
| سایت / مجتمع | — (فقط گروه‌بندی) | — | — | — |

هر انبار کد یکتا در سازمان (`WH-01`…) و انبار مادر اختیاری دارد (حداکثر ۴ سطح، بدون چرخه). انبار دارای موجودی یا رزرو فعال غیرفعال نمی‌شود و انبار دارای سابقه حذف نمی‌شود. قواعد: `app/services/warehouse_service.py`.

## ۴. جداسازی سازمان‌ها (Multi-tenancy)

جداسازی در لایه داده انجام می‌شود، نه در رابط کاربری (`app/core/tenancy.py`):

1. **خواندن:** همه کوئری‌های ORM خودکار به سازمان جاری محدود می‌شوند (لیست، شناسه مستقیم و رابطه‌ها).
2. **نوشتن:** رکورد جدید بدون سازمان، سازمان جاری را می‌گیرد؛ بدون سازمان جاری خطا می‌دهد.
3. **ارجاع:** رکوردی که به رکورد سازمان دیگر اشاره کند (مثلاً رسید با تأمین‌کننده یا انبار سازمان دیگر) ذخیره نمی‌شود (`TenantIsolationError` ← پاسخ ۴۰۳).
4. **API:** شناسه‌های سازمان دیگر «یافت نشد» (۴۰۴) برمی‌گردانند تا وجودشان فاش نشود.

## ۵. واژه‌نامه

| اصطلاح | فارسی | تعریف در پسینه |
|---|---|---|
| SKU | کد کالا | شناسه یکتا (بدون حساسیت به حروف) و **تغییرناپذیر** هر کالا در سازمان |
| Base UoM | واحد پایه | کوچک‌ترین واحد شمارش؛ همه مقادیر موجودی عدد صحیح این واحدند |
| UoM conversion | واحد فرعی | مثل «کارتن = ۱۲ عدد»؛ ضریب عدد صحیح ≥ ۲ تا تبدیل همیشه دقیق باشد |
| Lot / Batch | بچ / سری ساخت | گروهی از یک کالا با تاریخ تولید/انقضای یکسان (پرچم `lot_tracked`) |
| Serial | شماره سریال | شناسه تک‌تک واحدها (پرچم `serial_tracked`) |
| LPN | شناسه بسته/پالت | شناسه یک واحد حمل؛ در فصل‌های بعد |
| Putaway | جانمایی | قرار دادن کالای رسیده در محل نگهداری؛ در فصل‌های بعد |
| Picking | برداشت | جمع‌آوری کالای سفارش؛ در فصل‌های بعد |
| Allocation / Reservation | تخصیص / رزرو | کنار گذاشتن موجودی سالم برای یک سند (`stock_reservations`) |
| On hand | موجودی فیزیکی | `inventories.quantity` (شامل رزرو) |
| Free / ATP | موجودی آزاد | موجودی سالم منهای رزرو |
| Stock status | وضعیت کیفی | سالم، قرنطینه، توقیف، معیوب |
| Inventory document | سند انبار | رسید، حواله، اصلاحیه، ضایعات، انتقال، تغییر وضعیت، انبارگردانی، برگشت (`stock_documents`) |
| Ledger | دفتر گردش کالا | گردش‌های غیرقابل‌تغییر؛ موجودی هر ردیف = مجموع گردش‌هایش (`stock_movements`) |
| Reversal | سند برگشت | گردش‌های قرینه با `reversal_of_id`؛ سند اصلی «برگشت‌خورده» می‌شود |
| Idempotency key | کلید یکتایی درخواست | هدر `Idempotency-Key`؛ تکرار درخواست، سند یا سفارش دوم نمی‌سازد |
| Domain event | رویداد دامنه | ثبت غیرقابل‌تغییر «چه اتفاقی افتاد» در همان تراکنش (`domain_events`) |
| Partner | طرف تجاری | تأمین‌کننده، مشتری حقوقی/عمده یا شرکت حمل (`partners`)؛ مشتری نهایی سفارش‌ها در `customers` است |

## ۶. اسناد انبار

| نوع | پیشوند کد | برگشت با کاربر؟ | تولید |
|---|---|---|---|
| موجودی اول دوره | `OB` | ✓ | تعریف کالا با موجودی اولیه |
| رسید ورود کالا | `RC` | ✓ | `POST /inventory/movements` (با تأمین‌کننده و شماره فاکتور اختیاری) |
| حواله خروج سفارش | `GI` | — (از مسیر سفارش) | بارگیری سفارش |
| برگشت از سفارش | `RT` | — | عدم تحویل پس از بارگیری |
| اصلاحیه موجودی | `AJ` | ✓ | اصلاح دستی |
| ضایعات و کسری | `WO` | ✓ | ضایعات |
| انتقال | `TR` | ✓ (فقط ادمین؛ دو انبار) | `POST /inventory/transfers` |
| تغییر وضعیت کیفی | `QS` | ✓ | `POST /inventory/status-changes` |
| اصلاحیه انبارگردانی | `IC` | — (شمارش مجدد) | تأیید انبارگردانی |
| سند برگشت | `RV` | — | `POST /inventory/documents/{id}/reverse` |

برگشت وقتی رد می‌شود که موجودی آزاد کافی نباشد (مثلاً کالای رسیده بعداً رزرو شده باشد). سند برگشت هم کلید یکتایی می‌پذیرد.

## ۷. چرخه عمر کالا و مرز رویدادها

```
 تأمین‌کننده ──رسید (RC)──► [قرنطینه] ──بازرسی (QS)──► [سالم و آزاد] ──سفارش──► رزرو
                                │                          │                     │
                            معیوب/توقیف (QS)          انتقال (TR)            بارگیری (GI)
                                │                          │                     │
                           ضایعات (WO)               انبار دیگر          تحویل │ عدم تحویل (RT)
                                                                                      │
                                                                         ← برگشت به سالم و آزاد
```

هر پیکان یک تراکنش اتمی است: تغییر موجودی، گردش‌ها، سند و رویداد با هم ذخیره می‌شوند یا هیچ‌کدام. رویدادها در `after_flush` به‌طور مرکزی ساخته می‌شوند (`app/services/event_bus.py`)، پس هر مسیر کدی که سند ثبت کند رویدادش را هم دارد:

| رویداد | زمان |
|---|---|
| `stock.document.posted` | هر سند قطعی (با گردش‌هایش در payload) |
| `stock.document.reversed` | سند اصلی برگشت خورد |
| `stock.reserved` · `stock.reservation.released` · `stock.reservation.consumed` | چرخه رزرو |
| `product.created` · `product.updated` | داده پایه کالا (نام فیلدهای تغییرکرده) |
| `warehouse.created` · `warehouse.updated` | انبار |
| `partner.created` · `partner.updated` | طرف تجاری |

مصرف‌کننده‌ها (یکپارچه‌سازی، وب‌هوک در فصل‌های بعد) با `GET /wms/events?after_id=…` به ترتیب شناسه دنبال می‌کنند (فقط ادمین سازمان).

## ۸. داده پایه کالا و طرف‌های تجاری

**کالا:** نام کامل و کوتاه، SKU تغییرناپذیر، گروه، واحد پایه، واحدهای فرعی (`product_uoms`)، وزن ناخالص و خالص (خالص ≤ ناخالص)، ابعاد و حجم، ردیابی بچ/سریال/انقضا (انقضا بدون بچ ممکن نیست؛ ماندگاری به روز)، حداقل/حداکثر موجودی و نقطه سفارش پیش‌فرض. بارکد در کل سازمان یکتاست — هم بارکد کالا و هم بارکد واحدهای فرعی. کالای دارای سابقه حذف نمی‌شود، بایگانی می‌شود.

**طرف تجاری:** کد یکتا (`SUP-001`، `CUS-001`، `CAR-001`)، نقش‌های هم‌زمان، شخصیت حقوقی/حقیقی، شناسه ملی ۱۱ رقمی یا کد ملی ۱۰ رقمی با رقم کنترل، کد اقتصادی، شماره شبا با کنترل mod-97، کد پستی، موبایل، مهلت پرداخت، زمان تأمین (تأمین‌کننده)، نوع خدمت و الگوی لینک رهگیری (شرکت حمل). شناسه ملی و شبا برای مدیر انبار پوشانده است؛ ساخت و ویرایش فقط با ادمین سازمان و در گزارش فعالیت ثبت می‌شود (بدون مقدار فیلدهای حساس). هر کالا می‌تواند چند تأمین‌کننده با کد کالای تأمین‌کننده، زمان تأمین، حداقل سفارش و آخرین قیمت داشته باشد (`product_suppliers`).

## ۹. مایگریشن ۰۰۲۴ روی داده موجود

- انبارها کد `WH-01`… و نوع «عمومی» می‌گیرند؛ ردیف‌های موجودی بی‌انبار به اولین انبار سازمان می‌روند و ردیف‌های تکراری یک کالا در یک انبار ادغام می‌شوند.
- هر گردش قدیمی یک سند می‌گیرد (دو گردش هر انتقال و گردش‌های هم‌نوع هر سفارش/انبارگردانی یک سند مشترک) — دفتر بعد از مایگریشن همچنان سازگار است.
- سفارش‌های قبلی موجودی‌شان هنگام ثبت کم شده بود، پس `stock_state = issued` (یا `returned` برای سفارش‌های لغو/ناموفق/منقضی) می‌گیرند؛ سفارش‌های تازه از «رزرو» شروع می‌کنند.
- بارکدهای تکراری یک سازمان فقط روی قدیمی‌ترین کالا می‌مانند.

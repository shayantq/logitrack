# معماری انبارداری (WMS) — فصل ۱ تا ۱۰

این سند قواعد پایه، واژه‌نامه، چرخه عمر کالا و ساختار داده پایه پسینه را توضیح می‌دهد. منبع واحد نام‌ها و وضعیت‌ها در کد `app/core/wms.py` است و همین فهرست از `GET /wms/vocabulary` هم در دسترس است.

## ۱. قاعده‌های غیرقابل‌مذاکره

| قاعده | چطور تضمین می‌شود |
|---|---|
| موجودی هرگز با ویرایش مستقیم عدد عوض نمی‌شود | تنها مسیر، `stock_ledger.record()` است که همراه با یک **سند انبار** یک **گردش** ثبت می‌کند. محافظ `before_flush` هر تغییر بی‌سند در `quantity` یا `reserved_quantity` را با `LedgerViolationError` رد می‌کند. |
| وضعیت فیزیکی، کیفی، تخصیص و سند از هم جدا هستند | چهار محور جدا (بخش ۲). هر محور فقط از مسیر خودش تغییر می‌کند. |
| سند قطعی حذف یا بازنویسی نمی‌شود | ORM: ویرایش/حذف `StockMovement`، `DomainEvent` و سند قطعی متوقف می‌شود. PostgreSQL: تریگرهای مایگریشن ۰۰۲۴ حتی SQL مستقیم را رد می‌کنند. اصلاح فقط با **سند برگشت**. |
| جلوگیری از رزرو دوباره و رقابت هم‌زمان | قفل ردیف (`SELECT … FOR UPDATE`، همیشه به ترتیب `id`)، قید `reserved_quantity <= quantity` در دیتابیس، قید یکتای ردیف موجودی و `SAVEPOINT` برای ساخت هم‌زمان ردیف، و کلید یکتایی درخواست (Idempotency-Key). |

حالت نگهداری (`stock_ledger.maintenance`) فقط برای اسکریپت‌های نگهداری و داده نمونه است و هرگز در مسیر درخواست کاربر استفاده نمی‌شود.

## ۲. چهار محور وضعیت

```
             فیزیکی                 کیفی                    تخصیص                 سند
  ┌──────────────────────┐  ┌─────────────────────┐  ┌──────────────────┐  ┌───────────────┐
  │ کالا × انبار (ردیف     │  │ available  سالم      │  │ رزرو فعال         │  │ draft         │
  │ inventories)          │  │ quarantine قرنطینه   │  │ (stock_          │  │ posted  قطعی  │
  │ quantity = موجود       │  │ blocked    توقیف     │  │  reservations)   │  │ reversed      │
  │ گردش‌ها = تاریخچه     │  │ damaged    معیوب     │  │ موجودی آزاد =     │  │ canceled      │
  │                       │  │ هر وضعیت یک ردیف    │  │ موجود − رزرو      │  │               │
  └──────────────────────┘  └─────────────────────┘  └──────────────────┘  └───────────────┘
```

- **ردیف موجودی** = کالا × انبار × وضعیت کیفی (قید یکتای `uq_inventories_bucket`). فقط ردیف «سالم و آزاد» فروخته، رزرو، شمرده (انبارگردانی) و در نقطه سفارش حساب می‌شود.
- **رزرو** موجودی فیزیکی را تغییر نمی‌دهد؛ فقط آن مقدار را برای سفارش‌های دیگر قفل می‌کند. پایان رزرو: «مصرف» (حواله خروج) یا «آزادسازی» (لغو/انقضا).
- **وضعیت کالای سفارش** (`orders.stock_state`) جدا از وضعیت حمل است: `reserved` ← `issued` (بارگیری) ← `returned` (عدم تحویل)، یا `reserved` ← `released` (لغو/انقضا قبل از بارگیری).

## ۳. انواع انبار و سلسله‌مراتب

| نوع | نگهداری کالا | ارسال سفارش | رسید مستقیم | وضعیت پیش‌فرض رسید |
|---|---|---|---|---|
| عمومی، محصول نهایی، مرکز توزیع | ✓ | ✓ | ✓ | سالم |
| مواد اولیه | ✓ | — | ✓ | سالم |
| قرنطینه، مرجوعی | ✓ | — | ✓ | قرنطینه |
| در راه | ✓ | — | فقط با انتقال | سالم |
| سایت / مجتمع | — (فقط گروه‌بندی) | — | — | — |

هر انبار کد یکتا در سازمان (`WH-01`…) و انبار مادر اختیاری دارد (حداکثر ۴ سطح، بدون چرخه). انبار دارای موجودی یا رزرو فعال غیرفعال نمی‌شود و انبار دارای سابقه حذف نمی‌شود. قواعد: `app/services/warehouse_service.py`.

## ۴. جداسازی سازمان‌ها (Multi-tenancy)

جداسازی در لایه داده انجام می‌شود، نه در رابط کاربری (`app/core/tenancy.py`):

1. **خواندن:** همه کوئری‌های ORM خودکار به سازمان جاری محدود می‌شوند (لیست، شناسه مستقیم و رابطه‌ها).
2. **نوشتن:** رکورد جدید بدون سازمان، سازمان جاری را می‌گیرد؛ بدون سازمان جاری خطا می‌دهد.
3. **ارجاع:** رکوردی که به رکورد سازمان دیگر اشاره کند (مثلاً رسید با تأمین‌کننده یا انبار سازمان دیگر) ذخیره نمی‌شود (`TenantIsolationError` ← پاسخ ۴۰۳).
4. **API:** شناسه‌های سازمان دیگر «یافت نشد» (۴۰۴) برمی‌گردانند تا وجودشان فاش نشود.

## ۶. اسناد انبار

| نوع | پیشوند کد | برگشت با کاربر؟ | تولید |
|---|---|---|---|
| موجودی اول دوره | `OB` | ✓ | تعریف کالا با موجودی اولیه |
| رسید ورود کالا | `RC` | ✓ | `POST /inventory/movements` (با تأمین‌کننده و شماره فاکتور اختیاری) |
| حواله خروج سفارش | `GI` | — (از مسیر سفارش) | بارگیری سفارش |
| برگشت از سفارش | `RT` | — | عدم تحویل پس از بارگیری |
| اصلاحیه موجودی | `AJ` | ✓ | اصلاح دستی |
| ضایعات و کسری | `WO` | ✓ | ضایعات |
| انتقال | `TR` | ✓ (فقط ادمین؛ دو انبار) | `POST /inventory/transfers` |
| تغییر وضعیت کیفی | `QS` | ✓ | `POST /inventory/status-changes` |
| اصلاحیه انبارگردانی | `IC` | — (شمارش مجدد) | تأیید انبارگردانی |
| سند برگشت | `RV` | — | `POST /inventory/documents/{id}/reverse` |

برگشت وقتی رد می‌شود که موجودی آزاد کافی نباشد (مثلاً کالای رسیده بعداً رزرو شده باشد). سند برگشت هم کلید یکتایی می‌پذیرد.

## ۷. چرخه عمر کالا و مرز رویدادها

```
 تأمین‌کننده ──رسید (RC)──► [قرنطینه] ──بازرسی (QS)──► [سالم و آزاد] ──سفارش──► رزرو
                                │                          │                     │
                            معیوب/توقیف (QS)          انتقال (TR)            بارگیری (GI)
                                │                          │                     │
                           ضایعات (WO)               انبار دیگر          تحویل │ عدم تحویل (RT)
                                                                                      │
                                                                         ← برگشت به سالم و آزاد
```

هر پیکان یک تراکنش اتمی است: تغییر موجودی، گردش‌ها، سند و رویداد با هم ذخیره می‌شوند یا هیچ‌کدام. رویدادها در `after_flush` به‌طور مرکزی ساخته می‌شوند (`app/services/event_bus.py`)، پس هر مسیر کدی که سند ثبت کند رویدادش را هم دارد:

| رویداد | زمان |
|---|---|
| `stock.document.posted` | هر سند قطعی (با گردش‌هایش در payload) |
| `stock.document.reversed` | سند اصلی برگشت خورد |
| `stock.reserved` · `stock.reservation.released` · `stock.reservation.consumed` | چرخه رزرو |
| `product.created` · `product.updated` | داده پایه کالا (نام فیلدهای تغییرکرده) |
| `warehouse.created` · `warehouse.updated` | انبار |
| `partner.created` · `partner.updated` | طرف تجاری |

مصرف‌کننده‌ها (یکپارچه‌سازی، وب‌هوک در فصل‌های بعد) با `GET /wms/events?after_id=…` به ترتیب شناسه دنبال می‌کنند (فقط ادمین سازمان).

## ۸. داده پایه کالا و طرف‌های تجاری

**کالا:** نام کامل و کوتاه، SKU تغییرناپذیر، گروه، واحد پایه، واحدهای فرعی (`product_uoms`)، وزن ناخالص و خالص (خالص ≤ ناخالص)، ابعاد و حجم، ردیابی بچ/سریال/انقضا (انقضا بدون بچ ممکن نیست؛ ماندگاری به روز)، حداقل/حداکثر موجودی و نقطه سفارش پیش‌فرض. بارکد در کل سازمان یکتاست — هم بارکد کالا و هم بارکد واحدهای فرعی. کالای دارای سابقه حذف نمی‌شود، بایگانی می‌شود.

**طرف تجاری:** کد یکتا (`SUP-001`، `CUS-001`، `CAR-001`)، نقش‌های هم‌زمان، شخصیت حقوقی/حقیقی، شناسه ملی ۱۱ رقمی یا کد ملی ۱۰ رقمی با رقم کنترل، کد اقتصادی، شماره شبا با کنترل mod-97، کد پستی، موبایل، مهلت پرداخت، زمان تأمین (تأمین‌کننده)، نوع خدمت و الگوی لینک رهگیری (شرکت حمل). شناسه ملی و شبا برای مدیر انبار پوشانده است؛ ساخت و ویرایش فقط با ادمین سازمان و در گزارش فعالیت ثبت می‌شود (بدون مقدار فیلدهای حساس). هر کالا می‌تواند چند تأمین‌کننده با کد کالای تأمین‌کننده، زمان تأمین، حداقل سفارش و آخرین قیمت داشته باشد (`product_suppliers`).

## ۹. مایگریشن ۰۰۲۴ روی داده موجود

- انبارها کد `WH-01`… و نوع «عمومی» می‌گیرند؛ ردیف‌های موجودی بی‌انبار به اولین انبار سازمان می‌روند و ردیف‌های تکراری یک کالا در یک انبار ادغام می‌شوند.
- هر گردش قدیمی یک سند می‌گیرد (دو گردش هر انتقال و گردش‌های هم‌نوع هر سفارش/انبارگردانی یک سند مشترک) — دفتر بعد از مایگریشن همچنان سازگار است.
- سفارش‌های قبلی موجودی‌شان هنگام ثبت کم شده بود، پس `stock_state = issued` (یا `returned` برای سفارش‌های لغو/ناموفق/منقضی) می‌گیرند؛ سفارش‌های تازه از «رزرو» شروع می‌کنند.
- بارکدهای تکراری یک سازمان فقط روی قدیمی‌ترین کالا می‌مانند.

# عملیات انبار — فصل ۶ تا ۱۰

کد: `app/models_operations.py` (مدل‌ها)، `location_service`، `receiving_service`، `quality_service`، `putaway_service`، `stock_position_service` و هسته دفتر `stock_ledger`. مایگریشن: `0025_wms_operations`.

## ۱۰. ساختار فیزیکی و محل‌ها (فصل ۶)

- **سطح‌ها:** منطقه ← راهرو ← قفسه ← طبقه ← خانه. زیرمجموعه هر محل سطح پایین‌تری دارد (می‌توان سطحی را جا انداخت)، پس حلقه ممکن نیست. کد محل در انبار و بارکد در سازمان یکتاست (پیش‌فرض بارکد: «کد انبار-کد محل»).
- **کالا فقط در محل انتهایی** (بدون زیرمجموعه)، فعال و غیرمسدود می‌نشیند؛ به محلی که کالا دارد زیرمجموعه اضافه نمی‌شود. انبار بدون محل‌بندی همچنان کار می‌کند («بدون محل»).
- **نوع محل:** تخلیه و دریافت، نگهداری، برداشت، قرنطینه، آماده‌سازی، بارگیری. فقط موجودی تأییدشده‌ی محل نگهداری/برداشت **قابل تخصیص** است.
- **ظرفیت:** وزن (از وزن ناخالص کالا)، حجم (از ابعاد کالا) و پالت (از «تعداد در پالت» کالا). **قاعده اختلاط:** منع چند کالا، چند بچ از یک کالا یا کالای چند مالک در یک محل.
- هر دو هنگام **هر ورود** کالا به محل در دفتر گردش بررسی می‌شوند، با قفل ردیف محل تا دو ورود هم‌زمان با هم از ظرفیت رد نشوند. کاهش ظرفیت یا سخت‌تر کردن قاعده‌ای که موجودی فعلی را غیرمجاز کند، و مسدود/غیرفعال کردن محلی که رزرو سفارش‌ها را بی‌پوشش کند، رد می‌شود. محل دارای سابقه حذف نمی‌شود، غیرفعال می‌شود.

## ۱۱. رسید و دریافت (فصل ۷)

| نوع | مبدأ | نکته |
|---|---|---|
| خرید | تأمین‌کننده (الزامی) | شماره بارنامه/حواله هر تأمین‌کننده یکتاست |
| انتقال | انبار «در راه» | کالا با همان بچ/سریال از انبار در راه برداشته می‌شود؛ باقی‌مانده = «در راه» انبار مقصد |
| مرجوعی | مشتری، سفارش تحویل‌شده (اختیاری) | همیشه «در انتظار بازرسی» |
| پیش‌بینی‌نشده | — | سطرها هنگام دریافت ساخته می‌شوند |

- چرخه: **باز ← در حال دریافت ← بسته**؛ لغو فقط پیش از اولین دریافت.
- هر دریافت فیزیکی یک سند «رسید دریافت کالا» (`GR-`) در محل تخلیه با بچ، انقضا، سریال و مالک می‌سازد.
- شمارنده‌های هر سطر: مورد انتظار، دریافت‌شده، پذیرفته، مردود؛ در انتظار بازرسی = دریافت − پذیرفته − مردود؛ باقی‌مانده = انتظار − دریافت.
- کالای بچ‌دار/تاریخ‌دار/سریال‌دار بدون بچ/انقضا/سریال پذیرفته نمی‌شود؛ هر بچ فقط یک تاریخ انقضا دارد و هر سریال حداکثر یک‌جا در موجودی است (ایندکس یکتای جزئی). کالای منقضی فقط با وضعیت «آسیب‌دیده».
- **مغایرت:** اضافه تحویل بیش از تلورانس رسید و کالای خارج از برنامه فقط با دلیل؛ هنگام بستن، کسری (با دلیل الزامی)، اضافه و خارج از برنامه روی سطر ثبت می‌شود.
- **تکرار:** `Idempotency-Key` برای ساخت رسید و هر دریافت؛ دو دریافت هم‌زمان یک رسید با قفل ردیف رسید پشت سر هم اجرا می‌شوند.

## ۱۲. بازرسی کیفی و قرنطینه (فصل ۸)

- وضعیت‌ها: تأییدشده (`available`)، در انتظار بازرسی، قرنطینه، توقیف، مردود، معیوب، آسیب‌دیده. **وضعیت کیفی مستقل از محل است:** بازرسی و تغییر وضعیت کالا را جابه‌جا نمی‌کند؛ همان مقدار در همان محل با همان بچ/سریال به ردیف وضعیت دیگر می‌رود (سند `QI-`).
- مجوزها از `QUALITY_TRANSITIONS`: مدیر انبار بازرسی و نگه‌داشتن کالا را انجام می‌دهد؛ آزادسازی «توقیف» و «مردود» و برگرداندن معیوب/آسیب‌دیده به تأییدشده فقط با ادمین سازمان. همین جدول برای «تغییر وضعیت کیفی» دستی هم اعمال می‌شود.
- نتیجه بازرسی به سطرهای رسید نسبت داده می‌شود (پذیرفته/مردود) و برای کالای تأییدشده وظیفه جانمایی به قفسه و برای کالای مردود به محل قرنطینه ساخته می‌شود.
- فقط موجودی تأییدشده قابل تخصیص است؛ کالای قرنطینه/توقیف/مردود هرگز به سفارش نمی‌رسد.

## ۱۳. جانمایی و مدیریت نگهداری (فصل ۹)

- **ساخت وظیفه:** خودکار پس از دریافت/بازرسی برای کالایی که در محل تخلیه یا بدون محل مانده (اگر انبار مقصد مناسب دارد)، یا دستی. مجموع وظایف باز یک محدوده از موجودی آن بیشتر نمی‌شود.
- **پیشنهاد مقصد:** محل‌های انتهایی، فعال و غیرمسدود از نوع مناسب (تأییدشده ← نگهداری/برداشت؛ غیرقابل‌استفاده ← قرنطینه) که با ظرفیت و اختلاط جا دارند؛ اولویت: همان کالا و بچ، همان کالا، محل خالی، بقیه.
- **اجرا:** اسکن کالا (SKU، بارکد کالا یا بارکد واحد فرعی)، محل مبدأ (برای کالای بدون محل: کد انبار) و محل مقصد اجباری است. مقصد می‌تواند غیر از پیشنهاد باشد اگر از نوع مناسب باشد و جا داشته باشد. اجرای ناقص مجاز است. سند `PA-`.
- **خطا:** اسکن اشتباه (۴۲۲) یا نقض ظرفیت/قاعده، رد و در شمارنده خطای وظیفه و رویداد `putaway.task.failed` ثبت می‌شود (در تراکنش جدا، حتی وقتی عملیات رد شد). گزارش مشکل: مقصد پر/مسدود ← آن محل کنار می‌رود و مقصد دیگری پیشنهاد می‌شود؛ کالای آسیب‌دیده ← باقی‌مانده در همان محل «آسیب‌دیده» می‌شود؛ کالای ناموجود ← وظیفه بسته می‌شود (اختلاف فقط با انبارگردانی/اصلاحیه).
- **جابه‌جایی دستی** بین محل‌ها: سند `MV-` (قابل برگشت) با همان کنترل‌های مقصد.

## ۱۴. موجودی چندبعدی، دفتر و کاردکس (فصل ۱۰)

- دو سطح موجودی، هر دو فقط از `stock_ledger.record()`:
  - `inventories`: کالا × انبار × وضعیت — رزرو سفارش و نقطه سفارش.
  - `stock_balances`: همان × محل × مالک × بچ × سریال × انقضا.
- هر گردش (`stock_movements`) ردیف‌های ریز (`stock_movement_lines`) دارد. همیشه: مجموع ریزها = گردش، مجموع مانده‌های ریز = ردیف موجودی (`/inventory/ledger-check` هر سه را بررسی می‌کند). ردیف‌های ریز مثل گردش‌ها با تریگر PostgreSQL تغییرناپذیرند.
- **برداشت خودکار:** خروجی بدون محل/بچ مشخص به ترتیب FEFO (اول‌منقضی) و سپس قدیمی‌ترین ردیف برداشت می‌شود. حواله سفارش اول از موجودی قابل تخصیص، بقیه خروجی‌ها اول از موجودی غیرقابل تخصیص (منقضی، محل تخلیه) تا رزرو سفارش‌ها بی‌پوشش نماند. برگشت سفارش با همان بچ/سریال حواله برمی‌گردد.
- **سند برگشت** دقیقاً همان محل/بچ/سریال را برمی‌گرداند؛ اگر کالا بعداً جابه‌جا شده باشد، ابتدا باید جابه‌جایی بعدی برگشت بخورد.
- **وضعیت‌های مقدار** (`/inventory/positions`): فیزیکی، تأییدشده، قابل تخصیص، رزرو، قابل وعده (= قابل تخصیص − رزرو)، در انتظار بازرسی، قرنطینه/نگه‌داشته، در انتظار جانمایی، منقضی، امانی، در راه و ورودی مورد انتظار.
- **قابل تخصیص** = تأییدشده + در محل نگهداری/برداشت (یا بدون محل) + منقضی‌نشده + مال خود سازمان. کالای امانی (مالک دیگر) به سفارش‌های سازمان تخصیص نمی‌یابد.
- **کاردکس** (`/inventory/stock-card`، صفحه «کاردکس کالا»): مانده اول دوره، یک ردیف به ازای هر سند در محدوده (انبار، محل، بچ، وضعیت، بازه تاریخ) با ورود، خروج و مانده. جابه‌جایی‌هایی که در محدوده خالص صفرند پنهان‌اند، مگر نمایش داخلی روشن باشد.

## ۱۵. مایگریشن ۰۰۲۵ روی داده موجود

- هر ردیف موجودی یک ردیف ریز «بدون محل، بدون بچ» با همان مانده می‌گیرد و هر گردش قدیمی یک ردیف ریز روی آن — دفتر بعد از مایگریشن سازگار است (روی داده واقعی آزموده شد).
- قید وضعیت کیفی و نوع سند گسترش می‌یابد؛ طرف تجاری نقش «مالک کالا» و کالا «بازرسی هنگام ورود» و «تعداد در پالت» می‌گیرد.
- برگشت مایگریشن فقط وقتی مجاز است که هنوز محل، رسید، بازرسی، جانمایی یا موجودی بچ/سریال‌دار ثبت نشده باشد.

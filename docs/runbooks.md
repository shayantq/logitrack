# راهنمای رخداد و بازیابی

برای هر رخداد این ترتیب را نگه دارید: تشخیص، محدودسازی، تعیین مسئول، اطلاع‌رسانی، بازیابی، تطبیق، بستن، پیشگیری. دستورها را روی سرور در `/opt/logitrack` اجرا کنید.

## نقش‌ها در رخداد

| نقش | کار |
|---|---|
| فرمانده رخداد | تصمیم می‌گیرد، هر ۳۰ دقیقه وضعیت را ثبت می‌کند، پایان رخداد را اعلام می‌کند. |
| مسئول فنی | دستورها را اجرا می‌کند. |
| ارتباط با سازمان‌ها | پیام به مشتریان می‌فرستد. جزئیات فنی در پیام نمی‌آید. |

شدت: **بحرانی** یعنی سفارش ثبت یا تحویل نمی‌شود، یا خطر نشت یا از دست رفتن داده هست. **زیاد** یعنی یک بخش اصلی برای بعضی سازمان‌ها کار نمی‌کند. **متوسط** یعنی کار با کندی ادامه دارد.

## دیتابیس کند یا از کار افتاده

- **نشانه:** `/health` خطا می‌دهد، خطای ۵۰۳ «سرور مشغول است»، کاربران زمان پاسخ زیاد می‌بینند.
- **منبع حقیقت:** PostgreSQL. عددی را از روی کش یا صفحه باز قدیمی باور نکنید.
- **محدودسازی:**
  ```
  docker compose ps db
  docker compose exec -T db psql -U postgres -d logitrack -c "SELECT pid, state, wait_event_type, now()-query_start AS age, left(query,80) FROM pg_stat_activity WHERE state <> 'idle' ORDER BY age DESC LIMIT 15;"
  ```
- **ممنوع:** حذف دستی ردیف موجودی، `kill -9` پردازش postgres.
- **بازیابی:** کوئری گیرکرده را با `SELECT pg_cancel_backend(pid)` متوقف کنید. اگر دیسک پر است، اول فضا آزاد کنید.
- **تطبیق:** در `/app/exceptions` دکمه «بررسی دوباره» را بزنید تا مغایرت موجودی دیده شود.
- **شرط پایان:** `/health` سالم، خطای ۵۰۳ قطع، و `stock_mismatch` تازه‌ای نیست.

## Redis از کار افتاده

Redis هم صف Celery است و هم شمارنده سقف درخواست.

- **رفتار سامانه:** سقف درخواست به شمارنده داخل همان پردازش برمی‌گردد و کاربر خطا نمی‌بیند. پیام‌ها در `outbound_messages` می‌مانند و گم نمی‌شوند. گزارش‌ها تا برگشت Redis صف نمی‌شوند.
- **بررسی:** `docker compose ps redis` و `docker compose logs --tail=50 redis`
- **بازیابی:** `docker compose up -d redis`، بعد `docker compose restart celery_worker celery_beat`
- **تطبیق:** در `/app/platform` کارت «سلامت پس‌زمینه» را ببینید. صف پیام باید طی چند دقیقه خالی شود.

## Celery متوقف یا صف انباشته

- **نشانه:** کارت «سلامت پس‌زمینه» سن قدیمی‌ترین پیام را زیاد نشان می‌دهد، گزارش آماده نمی‌شود.
- **بررسی:** `docker compose ps celery_worker celery_beat` و `docker compose logs --tail=100 celery_worker`
- **بازیابی:** `docker compose restart celery_worker celery_beat`
- **اجرای دوباره:** وظیفه دوره‌ای ناموفق را از همان کارت با دلیل دوباره اجرا کنید. پیام حساس (رمز موقت، کد بازیابی) دوباره ارسال نمی‌شود و باید از نو صادر شود.

## فضای فایل پر شده

- **نشانه:** بارگذاری مدرک و پیوست خطا می‌دهد.
- **بررسی:** `df -h` و `docker system df`
- **ممنوع:** حذف دستی پوشه `media`؛ مدرک رانندگان و تحویل آن‌جاست.
- **بازیابی:** لاگ و ایمیج‌های بلااستفاده را پاک کنید: `docker image prune`

## سرویس پیامک یا ایمیل از کار افتاده

- **رفتار سامانه:** عملیات اصلی ادامه دارد. پیام تا ۵ بار با فاصله افزایشی تلاش می‌شود و بعد در کارت «سلامت پس‌زمینه» ناموفق دیده می‌شود.
- **بازیابی:** پس از برگشت سرویس، پیام‌های غیرحساس را از همان کارت دوباره بفرستید.

## مایگریشن ناموفق هنگام به‌روزرسانی

- **پیش از هر به‌روزرسانی:** بکاپ `pg_dump` (در دستورهای استقرار هست).
- **قاعده طراحی:** تغییر ناسازگار در دو نسخه جدا انجام می‌شود: اول افزودن (expand)، بعد از پایدار شدن حذف (contract). ستونی که نسخه قبلی هنوز می‌خواند در همان نسخه حذف نمی‌شود.
- **نشانه:** کانتینر `web` بالا نمی‌آید: `docker compose logs --tail=80 web`
- **بازیابی:** نسخه قبلی کد را برگردانید و اگر مایگریشن نیمه‌کاره مانده از بکاپ بازیابی کنید. `alembic downgrade` فقط وقتی امن است که داده تازه‌ای به ستون‌های حذف‌شونده نرفته باشد.

## برگشت نسخه با مدرک تحویل

`alembic downgrade` مایگریشن `0038` جدول‌های مدرک و ردیف‌های تازه را حذف می‌کند. پس از ثبت مدرک واقعی این کار را برای برگشت عملیاتی انجام ندهید. نسخه قبلی کد را برگردانید و جدول‌ها را نگه دارید: `delivery_attempts.photo_path` همچنان به تازه‌ترین فایل اشاره دارد.

## حساب اضطراری (break-glass)

اگر همه ادمین‌های پلتفرم قفل شدند:

```
docker compose exec web python create_admin.py
```

این کار باید همان روز ثبت شود: چه کسی، چرا، و کدام حساب ساخته شد. حساب پس از رفع مشکل غیرفعال می‌شود.

## سازمانی که باید متوقف شود

| نیاز | ابزار |
|---|---|
| جلوی کار تازه گرفته شود ولی سفرها تمام شوند | «تعلیق» در مدیریت سازمان |
| همه کاربران فوراً بیرون بروند | «غیرفعال» (سفرهای در راه هم قطع می‌شوند) |
| قرارداد تمام شده | «خروج سازمان»: اول خروجی، بعد ثبت خروج، پاک‌سازی پس از ۳۰ روز |

**پاک‌سازی خروج سازمان حذف کامل نیست.** داده شخصی و فایل‌ها پاک می‌شوند، ولی اسناد انبار و گزارش فعالیت غیرقابل‌تغییرند و می‌مانند. بکاپ‌های قدیمی تا پایان دوره نگهداری داده را دارند.

## پیدا کردن علت کندی

- **لاگ:** هر خط JSON است و `request_id` را دارد؛ همین شناسه در هدر `X-Request-ID` پاسخ و پیام خطا هست: `docker compose logs web celery_worker | grep <request_id>`
- **کوئری گران:** `bash scripts/slow-queries.sh`
- **متریک:** با `METRICS_TOKEN` در `.env`: `curl -H "Authorization: Bearer $METRICS_TOKEN" http://localhost:8000/internal/metrics`

## بازیابی واقعی (از دست رفتن سرور یا دیتابیس)

فقط با تصمیم فرمانده رخداد. پیش از هر کاری، از وضعیت فعلی (اگر چیزی مانده) بکاپ بگیرید.

1. سرور جایگزین یا همان سرور: docker و `git clone` مخزن روی همان کامیتی که پیش‌تر اجرا بود.
2. `.env` را از نسخه مدیر رمز برگردانید و کلید بکاپ را در `/root/.pasineh-backup-key` بگذارید (`umask 077`).
3. فایل‌های `nightly-db-*` و `nightly-media-*` تازه‌ترین نسخه را از سرور یا کامپیوتر مالک بیاورید و `sha256sum -c` بزنید.
4. فقط سرویس دیتابیس را بالا بیاورید: `docker compose up -d db`.
5. دیتابیس: `gpg --batch --pinentry-mode loopback --passphrase-file /root/.pasineh-backup-key --decrypt backups/nightly-db-X.sql.gz.gpg | gunzip | docker compose exec -T db psql -v ON_ERROR_STOP=1 -U postgres -d logitrack`
6. فایل‌ها: `gpg ... --decrypt backups/nightly-media-X.tar.gz.gpg | docker run --rm -i -v logitrack_media_data:/media alpine tar xzf - -C /media`
7. `docker compose up -d --wait`، سپس `alembic current` و `curl -fsS https://passineh.ir/health`.
8. زمان شروع و پایان را ثبت کنید؛ RTO واقعی همین است. عمر بکاپ استفاده‌شده RPO است.

## تمرین بازیابی

بکاپی که بازیابی نشده باشد بکاپ حساب نمی‌شود. این تمرین را هر ماه و بعد از هر تغییر بزرگ اجرا کنید:

```
cd /opt/logitrack && DRILL_ENV=production bash scripts/verify-backup.sh
```

**پیش‌نیاز:** docker روی میزبان، و برای فایل `.enc` یا `.gpg` خواندن کلید از `BACKUP_KEY_FILE` (پیش‌فرض `/root/.pasineh-backup-key`). روی کامپیوتر مالک، Git Bash و Docker Desktop کافی است. کلید را موقتاً در فایلی بیرون از OneDrive بگذارید و پس از تمرین پاکش کنید.

**اسکریپت چه می‌کند:** اگر کنار فایل `.sha256` باشد، اول آن را می‌سنجد. تازه‌ترین فایل `db-*`، `pre-deploy-*`، `nightly-*.enc` یا `nightly-db-*.gpg` را در کانتینر موقت بدون شبکه بازیابی می‌کند. فایل `nightly-media-*.tar.gz.gpg` را فقط باز و شمارش می‌کند. کلید نادرست یا فایل دستکاری‌شده با پیام روشن و کد خروج ۱ رد می‌شود. فایل فقط‌خواندنی وصل می‌شود. سالم بودن gzip، کامل بودن dump، جدول‌های اصلی و نسخه دیتابیس را می‌سنجد و نتیجه را در `backups/restore-drills.log` می‌نویسد. به دیتابیس زنده وصل نمی‌شود، پس تعداد ردیف را با آن مقایسه نمی‌کند.

**اگر شکست خورد:**

- `dump complete` پیدا نشد یا gzip خراب بود: فایل ناقص است. فایل قبلی را امتحان کنید و کار بکاپ شبانه را بررسی کنید.
- خطای کلید: کلید درست است؟ فایل با همان کلید ساخته شده؟
- خطای بازیابی: پیام `psql` را ببینید. اگر نقش برنامه (`APP_DB_USER`) در dump هست، کانتینر موقت آن را ندارد و این شکست از بکاپ نیست.

**تعریف‌ها:** `rpo_minutes` عمر فایل هنگام تمرین است و `rto_seconds` فقط زمان باز کردن و بازیابی دیتابیس. بالا آوردن برنامه و فایل‌های `media-*` در آن نیست، پس RTO واقعی سرویس بیشتر است.

**تمرین چیزی را عوض نمی‌کند.** بازیابی واقعی روی سرور اصلی کار جداگانه و با تصمیم فرمانده رخداد است.
